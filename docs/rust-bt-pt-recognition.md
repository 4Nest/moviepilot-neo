# Rust BT/PT 识别改进验证记录

## TMDB 繁体别名与篇章季号（neo 分支，尚未发布稳定版）

用户报告原始标题：

```text
[黒ネズミたち] 新网球王子 U-17 WORLD CUP 世界杯决赛成员决定战 / Tenipuri: U-17 Kesshou Member Ketteisen - 03 (Baha 1920x1080 AVC AAC MP4)
```

2026-10-15 实际 TMDB API 查询：完整简体片名、`Tenipuri: U-17 Kesshou Member Ketteisen` 各返回 0 条；完整繁体片名 `新網球王子 U-17 WORLD CUP 世界盃決賽成員決定戰` 返回 1 条，为 **205493 / 新网球王子 U-17世界杯篇**。其标准第 3 季名为“决赛成员决定战”，首播日期为 `2026-10-01`。响应以无凭据 JSON 保存在 `tests/fixtures/tmdb_tenipuri.json`，回归测试只离线复放。

Rust neo.3、neo.4 及 Python 回退都能提取完整中英文名、E03、1080p；原文没有显式季号。故此次修复放在 TMDB 模块：

- 保持原名、简体名、英文名的搜索顺序，失败后增加去重的繁体查询；名称比对统一简繁后仍要求完整相等。
- 已确认作品的完整别名以唯一明确季名结尾时，补全缺失的季号；本例得到 **S03E03**。不硬编码作品编号或季号，也不截断片名、泛化英文简称。
- 显式季号（含 S00）、季范围、自定义剧集组保持优先；短季名、通用季名、歧义、年份和集数冲突不用于推断。同步、异步及成功缓存命中使用同一规则。
- 本地修复已通过真实 TMDB 调用验证。当前运行的页面用临时识别词也能得到相同作品和 S03E03，识别词未保存到系统配置。

原有两组万条回归验证的是**标题、文件名和副标题字段解析**，不代表 TMDB 作品匹配率。新增测试 `tests/test_tmdb_title_alias.py` 覆盖从原始标题到作品及季号的匹配，Rust 另补原始标题的解析回归。已有失败缓存仍遵循原来的有效期；复测时可用 `cache=False` 或删除该条失败缓存，不能把缓存命中当成新查询结果。

本次匹配修复新增 26 条后端回归。后端全量 **23,446 passed、1 skipped**，全量 Pylint 无错误；Rust 标题专项 **984 passed**。测试均离线执行，后端使用全局网络守卫；真实 TMDB 验证单独在临时配置中执行。

## 副标题专项（neo.4 开发版，尚未发布）

新增固定 `subtitle_10k.jsonl.gz`：**148 条原始 audiences 主副标题、337 条构造边界案例、9,515 条说明文字变体**，共 **10,000 组唯一输入、60,394 个字段断言**。真实记录沿用已有采集，本轮没有新增抓站；BT 变体来自原有 Mikan、DMHY、AniBT、Nyaa 独立标注标题。原来的标题/文件名万条语料没有修改，两组分别回归。

| 集合 | neo.3 | neo.4 |
| --- | ---: | ---: |
| 真实主副标题 | 148 / 148 | 148 / 148 |
| 构造边界 | 263 / 337 | 337 / 337 |
| 说明文字变体 | 9,099 / 9,515 | 9,515 / 9,515 |
| 合计 | 9,510 / 10,000 | 10,000 / 10,000 |

490 组改善共享若干规则根因，并非 490 个独立 bug，也不代表全站准确率：

- 主标题确定的季集保持优先，副标题按缺失字段补充，不将单集和整季描述拼接。
- “第二季 全24集”可同时补季与集数；同类编号按出现顺序取值，“第08集”优先于日文别名里的“第2期”。
- 范围支持 `- ~ ～ – — 至`；拒绝倒序、零起始范围与越界数字；`13-24Fin` 正确计算为 12 集。
- 类型/演员/剧情/备注字段、更新计划和其他季度说明不污染当前资源；后续独立字段中的“全24集”仍可读取。
- “非 DIY / No DIY”不再增加 DIY 属性，肯定的 DIY 标记仍可识别。
- 拼音标题补中文名时排除简繁字幕、国语中字及季集等说明；保留副标题原文。
- Python 回退同步修复，补齐 PT 年度季号的四位数字读取，避免 `S2026` 截断为 `S202`。

这是确定格式的解析，不解析任意自然语言，也不推断播出计划等于实际收录内容。无额外上下文的“共24集”延续既有总集数约定；带“预计/计划/播出进度”等说明时不补入资源集数。

Rust 仓库的 `subtitle_samples.json` 保存原始记录和边界案例，`scripts/build_subtitle_corpus.py` 只读取独立标注并追加说明，不导入解析器、不按通过率选样。未确定电影类型时按接口约定标注“未知”；音乐样本仅检查可确定的字段。`subtitle_report.json` 保存最终同一语料的基线失败输入、字段差异、分组及耗时。

## 性能

本机 macOS arm64、Python 3.12、release wheel；同一万条输入，每组 3 轮、共 5 组，依次测不同模式，取每轮中位数。后端采用临时测试配置和 `custom_words=['#']`，计时前已预热。

| 路径 | 每一万条中位耗时 |
| --- | ---: |
| 单独 Rust neo.2 | 577.81 ms |
| 单独 Rust neo.3 | 575.93 ms |
| 后端 + neo.2 | 700.71 ms |
| 后端 + neo.3 | 700.95 ms |
| 后端纯 Python | 2966.54 ms |

新版完整调用性能与上一版基本持平，约为 Python 路径的 **4.23 倍**速度。不包含网络、数据库、TMDB 匹配或下载耗时。原始分组、每组计时和基线失败详情见 Rust 仓库 `tests/metainfo/recognition_10k_report.json`；前两轮历史报告仍保存在 `recognition_report.json`。

从后端根目录复测：

```sh
venv/bin/python -m pytest tests/test_bt_pt_recognition.py -q
venv/bin/python -m scripts.benchmark_recognition_10k --output /tmp/recognition-rust.json
venv/bin/python -m scripts.benchmark_recognition_10k --python-only --output /tmp/recognition-python.json
```

脚本先调用 `prepare_backend()` 隔离真实配置和数据库，再运行完整入口。可将旧 wheel 安装到独立目录，用 `PYTHONPATH` 运行同一脚本，避免更换当前安装。
